# Cloud telemetry contract (schemaVersion 2)

The gateway is the only device that talks to Azure IoT Hub. It sends two message types as
device-to-cloud telemetry, QoS 1, under its own IoT Hub device identity:

| `messageType` | When | Purpose |
|---|---|---|
| `summary` | every `GW_SUMMARY_MS` (default 60 s) | aggregated sensor-node and gateway readings plus health |
| `alert` | on each alarm transition, and as rate-limited reminders | impact, tilt, flame, sensor link loss |

Local 500 ms sensor telemetry (binary, see [PROTOCOL.md](PROTOCOL.md)) is **never forwarded
one-to-one**. It only feeds the summary.

Source of truth: [`vc_telemetry.cpp`](../lib/vehicle_core/src/vc_telemetry.cpp) (serialization)
and [`vc_gateway_app.cpp`](../lib/vehicle_core/src/vc_gateway_app.cpp) (when and what). The
examples below were **generated by the host integration harness** (`pio test -e native -f
test_integration -v`, lines starting `[example]`): the real sensor and gateway code running on
simulated inputs (23.4 °C / 48 % on both DHT11s, 21 °C / 40 % on the DHT22, level IMU, a
simulated clock starting 2025-10-25T12:00:00Z). They are not measurements.

**Changes from schemaVersion 1:** sensors can report `"status": "disabled"` (not fitted); the
flame and potentiometer moved into `gateway.flame {status, pct, active}` and
`gateway.pot {status, pct}`; `sensorNode.impacts`/`shockEdges` moved into
`sensorNode.shock {status, impacts, edges}`; `pir` gained `status`; `tiltActive` is `null` when
no IMU is fitted; `health` gained `queueHighWater`, `minFreeHeap`, `rx.badTag`, `rx.overflows`.

## MQTT properties

Every message is published on `devices/{gatewayDeviceId}/messages/events/` with this property
bag (built with `az_iot_message_properties_append`, ≤ 91 bytes for the default ids):

| Property | Value |
|---|---|
| `$.ct` (content type) | `application/json` |
| `$.ce` (content encoding) | `utf-8` |
| `$.mid` (message id) | stable id: alerts `eventId`, or `eventId:r<n>` for reminders; summaries `gatewayId:gatewayBootId:s<seq>` |
| `messageType` (application) | `summary` or `alert`, usable in IoT Hub routing queries |

## Envelope (all messages)

| Field | Type | Meaning |
|---|---|---|
| `schemaVersion` | int | `2`. Consumers must reject versions they don't support. |
| `messageType` | string | `summary` \| `alert` |
| `gatewayId` | string | the gateway's IoT Hub device id |
| `gatewayBootId` | int | gateway boot counter (NVS), increments every boot |
| `seq` | int | per gateway boot, +1 per created message; restarts at 1 after reboot. (`gatewayBootId`, `seq`) is unique. |
| `uptimeMs` | int | gateway `millis()` when the message was **created** (wraps after ~49.7 days) |
| `ts` | string \| null | gateway UTC time (ISO 8601, ms, `Z`) when the message was created; `null` if `timeValid` is false |
| `timeValid` | bool | gateway clock synchronised by SNTP to a plausible time |

A message that was queued during an outage keeps its original `ts`/`seq`. It is re-sent
byte-for-byte, so `ts` is creation time, not upload time.

| Field | Unit / values | Notes |
|---|---|---|
| `windowMs` | ms | configured window length |
| `sensorNode.link` | `up` \| `lost` \| `never_seen` \| `unconfigured` | |
| `sensorNode.lastRxAgeMs` | ms \| null | since the last *accepted* sensor packet |
| `sensorNode.bootId` | int | sensor boot counter of the latest packet |
| `sensorNode.synthetic` | `true` only if present | data came from synthetic-sensor mode, **not real measurements** |
| `sensorNode.packets` | count | accepted telemetry packets in the window (~120 at 2 Hz) |
| `*.status` | `ok` \| `stale` \| `error` \| `absent` \| `calibrating` (IMU) \| `disabled` \| `no_data` | `stale` = cached value older than the freshness limit; `absent` = fitted but never answered; `disabled` = not fitted (build flag) |
| `dht11[i].ageMs` | ms \| null | age of the latest value when it was sent |
| `dht11[i].samples` | count | **distinct** measurements in the window. The cached value repeated in every packet is counted once; stale values never. |
| `dht11[i].tempC`, `humidityPct` | °C, %RH | `{last,min,max,avg}` over distinct fresh samples, or `null` if none |
| `imu.accelG` | g | magnitude \|a\| of the latest sample per packet: `{last,max}` |
| `imu.peakAccelG` | g | max \|a\| over all ~100 Hz samples in the window |
| `imu.rollDeg`, `pitchDeg` | degrees | complementary-filter angles about chip X / Y |
| `imu.rateHzMin` | Hz | lowest per-second IMU update rate reported in the window |
| `imu.maxGapMs` | ms | largest gap between IMU updates in the window |
| `tiltActive` | bool \| null | sensor's tilt alarm state at the latest packet (`null` without IMU) |
| `pir.active` / `rises` / `activeFraction` | bool / count / 0..1 | latest state, rising edges, fraction of packets with motion |
| `shock.impacts`, `shock.edges` | count | impact records and raw shock-pin edges in the window |
| `lost.*` (only when non-zero) | count | `impactOverflows` (ISR ring full), `eventsDropped` (retransmit queue full), `eventsExpired` (never acknowledged), `linkRestarts` |
| `gateway.dht22` | as `dht11[i]` | gateway's own DHT22 (every successful 3 s read counts) |
| `gateway.flame.pct` | 0..100 | uncalibrated IR-intensity index from the flame module's analog output, `{last,max}` |
| `gateway.pot.pct` | 0..100 | potentiometer position, `{last,max}` |
| `health.queueDepth` / `queueHighWater` | messages | outbox occupancy now / since boot |
| `health.alertsDropped` | count | alerts or reminders evicted or refused by the full outbox |
| `health.rx.*` | count | ESP-NOW: accepted, rejected (all reasons), replay, unknownPeer, badTag, receive-queue overflows |
| `health.estMeterUnits` | count | local estimate of metered messages since boot (see below) |

## `alert`

Harness output, impact 5 s after boot (499 bytes):

```json
{
  "schemaVersion": 2, "messageType": "alert", "gatewayId": "vehicle-gateway-01",
  "gatewayBootId": 1, "seq": 1, "uptimeMs": 5202,
  "ts": "2025-10-25T12:00:05.202Z", "timeValid": true,
  "eventId": "sensor-node-01:1:1", "alertType": "impact", "state": "detected", "reminder": 0,
  "source": { "role": "sensorNode", "deviceId": "sensor-node-01", "bootId": 1, "detectedUptimeMs": 5000 },
  "eventTs": "2025-10-25T12:00:05.002Z", "eventTsSource": "gateway_estimate",
  "receivedTs": "2025-10-25T12:00:05.202Z",
  "details": { "peakAccelG": 2.6, "pulseCount": 3 }
}
```

(The simulated shock happened at 12:00:05.000; the estimate is 2 ms off, the simulated radio
delay. `receivedTs` is 200 ms later because an impact is reported when its 200 ms refractory
window closes.)

First reminder of a tilt alarm, 10 minutes after activation (468 bytes): same `eventId`,
`source` and `eventTs` as the activation; `ts` is the reminder's creation time.

```json
{
  "schemaVersion": 2, "messageType": "alert", "gatewayId": "vehicle-gateway-01",
  "gatewayBootId": 1, "seq": 12, "uptimeMs": 611021,
  "ts": "2025-10-25T12:10:11.021Z", "timeValid": true,
  "eventId": "sensor-node-01:1:1", "alertType": "tilt", "state": "active", "reminder": 1,
  "source": { "role": "sensorNode", "deviceId": "sensor-node-01", "bootId": 1, "detectedUptimeMs": 11020 },
  "eventTs": "2025-10-25T12:00:11.021Z", "eventTsSource": "gateway_estimate",
  "receivedTs": "2025-10-25T12:00:11.021Z",
  "details": {}
}
```

| Field | Values | Notes |
|---|---|---|
| `eventId` | `deviceId:bootId:counter` | identifies one detection or transition. Sensor events use the sensor's boot id and event counter; gateway alarms use the gateway's. Stable across all retransmissions; boot ids are never reused (PROTOCOL.md §3). |
| `alertType` | `impact` \| `tilt` \| `flame` \| `sensor_link_lost` | |
| `state` | `detected` (impact, instantaneous) \| `active` \| `cleared` | each transition is its own event |
| `reminder` | 0, or n ≥ 1 | n-th reminder of a still-active alarm. It repeats the activation's `eventId`, `source`, `eventTs` and `receivedTs`. |
| `source.role` / `deviceId` / `bootId` | | the device that detected the condition (for `sensor_link_lost` the gateway detects it about `sensor-node-01`) |
| `source.detectedUptimeMs` | ms | detection time on the **source** device's own monotonic clock |
| `eventTs` | ISO 8601 \| null | wall-clock detection time, if known |
| `eventTsSource` | `gateway_clock` \| `gateway_estimate` \| null | `gateway_estimate`: the sensor has no wall clock, so the gateway computes `receipt time − (sensor send uptime − sensor detection uptime)` |
| `receivedTs` | ISO 8601 \| null | sensor events only: when the gateway accepted the event |
| `details.peakAccelG` | g | impact: max \|a\| in the ~320 ms of 20 ms buckets around detection; omitted without an IMU |
| `details.pulseCount` | count | impact: shock edges inside the 200 ms refractory window |
| `details.angleDeg` | degrees | tilt: max(\|roll\|,\|pitch\|) at activation, or the peak during the episode when cleared |
| `details.flamePct` | 0..100 | flame: index at activation, peak when cleared, latest for reminders |
| `details.silentMs` | ms \| null | link loss: time since the last accepted sensor packet (`null` if never seen since gateway boot) |
| `source.synthetic` | `true` only if present | event came from synthetic-sensor mode |

A non-finite value is omitted from `details` (or `null` elsewhere), never written as `nan`.
**Impact** means the shock sensor produced a pulse, reported as a possible collision. It is not
a validated crash classification.

## Consumer rules

* Reject unknown `schemaVersion` values. Treat unknown extra fields as additive.
* De-duplicate on `$.mid` (or `eventId` + `reminder`). A message whose PUBACK was lost is
  re-sent with identical bytes and `$.mid`; an event retransmitted across a gateway reboot can
  arrive twice with the same `eventId`.
* `null` means no valid value. Statuses explain why.
* Counters are per window. Sequence numbers restart when `gatewayBootId` changes.

## Message sizes and daily quota

Metering rules (Microsoft Learn, *IoT Hub quotas and throttling* and *Understand IoT Hub
pricing*, checked 2026-10-25): device-to-cloud messages are metered in **0.5 KB blocks on the
free tier** and **4 KB blocks on basic/standard tiers**, by body **plus properties**; MQTT
connects, keep-alives and acks are not charged. Daily allowance per unit: **Free 8,000**,
**B1/S1 400,000** messages. IoT Hub also stamps its own system properties on ingress; how those
count cannot be observed from the device, so these are estimates.

**Measured from the implementation.** The accelerated 24-hour integration run
(`test_accelerated_24h_run`: 60 s summaries, an impact every 7 minutes, a 40-minute tilt every
3 hours with 10-minute reminders, a cloud drop every 4 hours, one 2-minute radio outage, 5 %
radio loss) produced these real messages (default ids `vehicle-gateway-01` / `sensor-node-01`):

| Stream | Messages / day | Body (min / avg / max) | Properties | Free-tier blocks | B1/S1 blocks |
|---|---|---|---|---|---|
| summary | 1,440 | 1,310 / 1,533 / 1,614 B | ≤ 91 B | 5,758 (mostly 4 each: body + properties > 1,536 B) | 1,440 |
| alert (206 impacts, 48 tilt incl. reminders, 2 link-loss) | 256 | 445 / 504 / 512 B | ≤ 88 B | 512 (2 each) | 256 |
| **total** | 1,696 | | | **6,270 ≈ 78 % of 8,000** | **1,696 ≈ 0.4 % of 400,000** |

Summary size grows with the number of fields that have values (every DHT/IMU statistic is a
`{last,min,max,avg}` object), with longer device ids, and with the optional `lost` object.
Values above are from simulated readings; real readings with more digits are slightly larger.

* **Free tier:** the default configuration fits, but with little margin for alert-heavy days.
  `-D GW_SUMMARY_MS=120000` roughly halves the dominant term (≈ 2,900 + alerts). Shorter
  device ids also help.
* **B1/S1:** every message is one block; usage is dominated by the message count.
* A message re-sent after a lost PUBACK is metered again if the first copy arrived. None
  occurred in the 24 h run (the hub received exactly 256 alerts for 256 events); the
  `test_cloud_disconnects_and_delayed_acks` scenario produces them deliberately.
* `health.estMeterUnits` is the gateway's own running estimate since boot (body + property bag,
  `GW_METER_BLOCK_BYTES` = 512 by default). It does not know the hub-wide remaining allowance,
  which the Azure portal shows (IoT Hub → Overview → daily message limit).
